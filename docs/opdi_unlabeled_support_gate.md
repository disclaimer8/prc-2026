# OPDI: проверка дополнительного наблюдения без меток

`scripts/opdi_support_gate.py` измеряет четыре разные ступени: FLIGHT-популяция источника → согласованные пары событий одного объекта → уникальные совпадения с наблюдаемыми строками PRC → сенсорная поддержка при известном ADS-B coverage<2. Он не открывает цели, прогнозы, OOF и модели и не оценивает выигрыш.

```sh
.venv/bin/python scripts/opdi_support_gate.py \
  --repo /home/a1/prc-2026 \
  --output /tmp/opdi_support_gate_20261005
```

Выходной каталог должен быть новым. В нём остаются `report.json` и `matched_support.parquet` с разрешёнными наблюдаемыми полями/флагами. Временные16шардов удаляются после завершения. Источники не меняются. Polars/OMP/BLAS ограничены двумя потоками; производственный запуск выполняет владелец под cgroup MemoryMax=3G/CPUQuota=200%. Пиковая память будет записана фактическим запуском; синтетическая проверка не доказывает производственный RSS.

Читаемые колонки заданы белыми списками в `READ_COLUMNS`. PRC/ADS-B сначала проецируются PyArrow на эти колонки; в provenance хешируется только проекция, а не весь файл с целями. Нативный PRC MVT_ID физически DOUBLE: разрешены лишь конечные целые значения в точном диапазоне ≤2^53. OPDI/OSM идентификаторы не проходят через float; repaired December `opdi_flight_id` сохраняет знак нативного FLIGHT ID.

Сопоставление не подбирается по покрытию: callsign без whitespace в верхнем регистре + ADEP, минимальный публичный take-off, иначе first-xing-fl50, иначе first_seen, фиксированное включительное окно `anchor−MVT∈[−900,+1800]с`. Обе степени считаются в полном графе кандидатов, до удаления неоднозначностей. Не выбирается ближайший из нескольких. Повторное использование OPDI ID двумя MVT исключает обе связи. Отчёт отдельно считает типы якорей и пропущенный callsign.

Группировка пары выполняется глобально, между всеми окнами, по точным native flight ID + osm_id + aeroway + airport. Нужен ровно один вход и один выход, положительное время, совпадение обеих длительностей `info` с разностью времён, география в15км от центра OSM-стоянок указанного аэропорта и совпадение этого аэропорта с ADEP/ADES. Односторонние/повторные/несогласованные группы получают отдельные флаги. Неверный JSON/идентификатор консервативно запрещает пары затронутого рейса. Дубликат любого использованного EVENT ID между окнами останавливает аудит вместо повторного счёта. Несогласованные FLIGHT-метаданные одного ID исключаются. Missing EVENT-окна и отсутствующие дни FLIGHT отражаются отдельно; отсутствие записи ADS-B не маскируется под известный coverage0.

## Что означает «согласованная пара»

**Это наблюдаемый интервал проекции на полигон, а не доказанная занятость ВПП на земле.** Проверен официальный исходник [v002, commit8bf973d0997d3ef202e44e3ecc6426c714de0086](https://github.com/euctrl-pru/OPDI/blob/8bf973d0997d3ef202e44e3ecc6426c714de0086/python/v2.0.0/04_opdi_flight_events_etl.py#L403):

- Строки413–424: `baro_altitude_c*3.28084` переводится в футы; остаётся flight_level≤20, то есть **абсолютная очищенная барометрическая высота≤2000ft**. Затем применяется H3res12-полигон и аэропорт ADEP/ADES/возможный аэропорт. Нет проверки on_ground, скорости, фазы либо высоты над аэродромом.
- Строки439–472: entry/exit — минимальное/максимальное время совпавших точек, новая trace при разрыве>300с. Это не интерполированное время пересечения границы; координаты/высота выбраны отдельными first/last, без явного argmin/argmax по времени.
- Строки675–705: `altitude_ft` экспортируется как `altitude`, версия `events_v0.0.2`. [Очистка `_c`](https://github.com/euctrl-pru/OPDI/blob/8bf973d0997d3ef202e44e3ecc6426c714de0086/python/v2.0.0/02_osn_tracks_etl.py#L147) сглаживает неправдоподобную вертикальную скорость в окне±300с; это не поправка на высоту аэродрома.

Следовательно, низкий заход, пролёт или участок после отрыва могут образовывать пару. Этот вывод относится к проверенному историческому генератору; соответствие каждому опубликованному shard отдельно не доказано. Аудит сохраняет наличие/диапазон исходной высоты и хронологию до/через/после публичного take-off и landing, **без нового высотного порога**. Геометрическая/временная согласованность не переименовывается в ground-valid.

Статус `complete_unlabeled_audit` означает завершение проверки, даже если исходный OPDI остаётся44/45 или вывод отрицательный. Наличие хотя бы одной пары во всех14месяцах — лишь наличие, не стабильная вероятность приёма. Возобновлять исходное предложение residual-модели «runway occupancy» на основании таких пар нельзя: сначала нужен фактический вывод безметочной проверки фаз и дополнительной поддержки. Возможные честные итоги — отсутствие нового пригодного ground-сигнала либо существенно более узкая наблюдаемая популяция.

Тесты: `python -m unittest discover -s tests -p 'test_opdi_*'`. Синтетические случаи покрывают пары между окнами, разные объекты, повторы, плохую географию/JSON/длительность, дробные ID, публичную фазу, явные проекции без запрещённых колонок, глобальную неоднозначность и отсутствующий requested-архив.
