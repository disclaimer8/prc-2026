# Полный каталог OPDI: проверка доступности 04.10.2026

Проверены официальный портал, официальный репозиторий, HTTP HEAD всех файлов нужного периода, 32-МБ образец MEASUREMENT и небольшой адресный образец геометрии. Основной код, модели, журнал и очереди не менялись. Разрешение организатора на использование OPDI принято как установленный пользователем факт; повторная проверка допуска не является блокером этой работы.

**Действительно новая информация при полной загрузке:** измеренное накопленное расстояние, точные идентификаторы событий для связи EVENT→MEASUREMENT, содержимое `info` с объектами аэродрома, и события прилетающих рейсов, которые старый фильтр по `adep` удалял. Координаты уже есть в локальных `ev_*`; все типы событий тоже уже сохранялись, хотя комментарий старого загрузчика обещает только наземные. Следовательно, сами дополнительные названия событий и уже сохранённые координаты новым источником считать нельзя. Прирост качества не измерялся.

## Что опубликовано

Официальный каталог и скачанные HTML-страницы подтверждают **v0.0.2, январь 2022 — июль 2026 включительно**: 55 месячных FLIGHT, 168 ссылок EVENT и 168 MEASUREMENT с интервалом 10 суток. Последний интервал называется `20260729_20260808`, но заявленная дата окончания покрытия — 31 июля; имя файла не доказывает наличие августа. [Каталог](https://www.opdi.aero/data), [FLIGHT](https://www.opdi.aero/flight-list-data), [EVENT](https://www.opdi.aero/flight-event-data), [MEASUREMENT](https://www.opdi.aero/measurement-data).

Точные URL:

```text
https://www.eurocontrol.int/performance/data/download/OPDI/v002/flight_list/flight_list_{YYYYMM}.parquet
https://www.eurocontrol.int/performance/data/download/OPDI/v002/flight_events/flight_events_{YYYYMMDD}_{YYYYMMDD_end}.parquet
https://www.eurocontrol.int/performance/data/download/OPDI/v002/measurements/measurements_{YYYYMMDD}_{YYYYMMDD_end}.parquet
```

Сетка EVENT/MS непрерывная, отсчитывается от **2022-01-01**, а не от первого числа каждого месяца. Для всего 2025 + января/июля 2026 нужны **45 уникальных интервалов**: непрерывно `20241226_20250105` … `20260130_20260209`, затем `20260629_20260709`, `20260709_20260719`, `20260719_20260729`, `20260729_20260808`.

Текущий официальный экспорт выбирает рейсы по `FLIGHT.first_seen >= start AND < end`, затем все их события и измерения. Это важно при стыковке соседних суток/месяцев: фильтровать только `event_time` в пределах имени архива нельзя. Экспорт может включать событие за правой границей окна. [Зафиксированный исходник экспортёра](https://github.com/euctrl-pru/OPDI/blob/5bf5e753f064c8245b3d9be9e954326ef6d24162/src/opdi/output/parquet_exporter.py).

Для загрузки достаточно держать один исходный архив, читать Parquet последовательно, сохранять отобранные строки и затем освобождать исходник. Максимальный исходный архив меньше 554 МБ; весь сырой набор одновременно хранить не требуется. Фактический размер отфильтрованных полных таблиц пока не измерен.

## Схемы и проверенный образец

**FLIGHT — проверены локальные оригиналы с совпавшими текущими размерами HEAD.** Общие поля:

```text
id, icao24, flt_id, dof, adep, ades, adep_p, ades_p,
registration, model, typecode, icao_aircraft_class, icao_operator,
first_seen, last_seen, version
```

В `flight_list_202501.parquet`: 1,036,088 строк, `id:uint64`, времена `timestamp[us]`, дополнительное `unix_time:int64`; первые записи имеют `version=v2.0.0`. В январе 2026: 709,137 строк; в июле: 1,746,344; `id:int64`, времена строковые, образцы `version=v0.0.2`. Поэтому версию каталога нельзя считать единственной версией строк, а знаковые типы и время нужно нормализовать без потери ID. `flt_id` содержит правые пробелы. На схеме портала есть опечатка `typdecode`; фактическое поле — `typecode`.

**EVENT — опубликованная схема:** `id, flight_id, type, event_time, longitude, latitude, altitude, source, version, info`. Конкретный свежий EVENT-образец проверяется отдельно в основном процессе загрузки; здесь оригинал EVENT не скачивался. Локальный `ev_20241226_20250105.parquet` имеет 536,201 строку и колонки `flight_id,icao24,flt_id,adep,ades,type,t,longitude,latitude,altitude,source,version`: отсутствуют `id` и `info`. Источник: `scripts/get_opdi_events.sh` и `scripts/get_opdi_events_2025.sh`; после join они выбирают эти 12 полей, без фильтра `type`.

**MEASUREMENT — скачан и проверен полный малый образец:**

[measurements_20251231_20260110.parquet](https://www.eurocontrol.int/performance/data/download/OPDI/v002/measurements/measurements_20251231_20260110.parquet), локально `/private/tmp/opdi_full_catalog/measurements_20251231_20260110.parquet`.

```text
id: int64
 event_id: int64
 type: string
 value: double
 version: string
```

1,596,062 строки, 2 row groups, 798,031 уникальный `event_id`. Каждый ID имеет ровно две строки и два разных типа, `version=v0.0.2`:

| Реальная строка type, регистр важен | Строк | Минимум | Максимум |
|---|---:|---:|---:|
| `Distance flown (NM)` | 798,031 | 0 | 10,990.287749 |
| `Time Passed (s)` | 798,031 | 0 | 81,800 |

Первый пример: `event_id=-6191440516593477393`, время 690 s, расстояние 77.48997946460626 NM. В другой паре: `event_id=6352646872448782057`, 150 s и 2.8960101069063438 NM. Это только подтверждение данных, не проверка наземного рейса или полезности для taxi-out.

По методологии расстояние — сумма геодезических расстояний между последовательными исходными state vectors с начала наблюдения. Разность двух cumulative distance содержит информацию о пройденном пути между событиями, которую не восстановить только из прямого расстояния между конечными координатами. `Time Passed (s)` преимущественно дублирует временные разности; его наличие само по себе не означает нового сигнала. CO2 упоминается как концептуальный пример, но в проверенном v002-образце нет такого типа. [Методология](https://www.opdi.aero/methodology).

## Как сохранить действительно полный целевой срез

1. Использовать существующие 14 полных FLIGHT и сохранить все их колонки. Для событий построить множество `id` по `adep IN APS OR ades IN APS`; отдельно учитывать временную периферию для связки предыдущего прилёта.
2. По одному скачать доступные 44 EVENT-архива, сохранить **все исходные колонки**, включая `id`, `info`, исходное `event_time`, `source`, `version`; выделить связь с FLIGHT. Не обрезать типы, координаты или события на правой границе имени файла. Пробел октября записать явно.
3. По одному скачать 45 MEASUREMENT, фильтровать `event_id` по сохранённым EVENT IDs. Для октябрьского окна без EVENT хранить явный статус невозможности join, а не выдавать нулевые измерения за отсутствие движения.
4. Нормализовать ID в строку без промежуточного float/int64, поскольку 2025 содержит uint64, а 2026 — signed int64. Время парсить по схеме, callsign обрезать справа; сохранить исходники полей для аудита.
5. Первым измерением качества данных сделать фактический EVENT↔MEASUREMENT join, непустоту `info`, наземные пары событий и airport geography в 2025 и обоих ranking-месяцах. Разности distance/time считать только внутри одной траектории, в верном порядке, с географической проверкой и отделением прилёта от вылета.

Это подготовка наблюдений, а не разрешение на CV или обещание улучшения. Любая новая модель или калибровка требует отдельной текущей регистрации и временной проверки относительно боевого контроля. Уже закрытые повторные timestamp-калибровки E159 не являются основанием отвергать ещё не использованные distance/ID/info/arrival данные, но и наличие этих данных не доказывает выигрыш.

Все временные материалы этого прохода находятся в `/private/tmp/opdi_full_catalog`. Загруженный основной образец данных — 32,144,541 B MEASUREMENT; остальные сетевые тела — небольшие JSON/HTML/source и адресные фрагменты ZIP. Ни один полный большой EVENT/trajectory архив здесь не скачивался.
