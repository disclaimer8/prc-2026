# PRC 2026: новые направления для выхода в топ-3

Конфиденциально, как REVIEW_BRIEF.md. Подготовлено 14–15.09.2026. Это исследовательский отчёт и дизайн экспериментов; модели, признаки, исходные данные и сабмиты не изменены. Новые модели ниже ещё не обучены. Числа в разделе «Свежие проверки» получены чтением текущих parquet, а не перенесены из предыдущих ревью.

## Решение

Вернуть исследовательскую работу в план. Закрытие всей темы регрессии, всех строк без NM и практически всего остатка преждевременно. Проверенные ранее групповые поправки и калибровки не измеряют предел информации в последовательностях, связанных записях и внешних идентификаторах самолётов.

Моя первая ставка — восстановление связей между событиями и бортами. Вторая — обучение смеси непосредственно под ошибку в секундах. Третья, более экспериментальная, — совместная модель последовательности движений аэропорта. Отдельно есть небольшой, дешёвый источник улучшения: регулярность новых номеров из самого ranking.

Публичный API при проверке показал лучшие результаты разных команд: 245,0207; 247,5879; **252,9192**. При исходных 274,93 из брифа до третьего места нужно снять 22,01 с RMSE, то есть **15,37% SSE**, или примерно **4,0065·10⁹ секунд²** на 344 841 строке. Это текущая планка, не прогноз финального топ-3. API возвращает сабмиты, поэтому места здесь посчитаны по уникальным командам, а не по первым трём строкам.

Источник: [официальная страница ранжирования с ссылкой на API](https://prc-data-challenge-2026.netlify.app/ranking.html). Снимок первых 50 сабмитов сохранён вне репозитория: `/private/tmp/prc-leaderboard-review-20260914.json`. Его достаточно для определения первых трёх уникальных команд; текущая позиция gentle-igloo целиком заново не пересчитана.

## Свежие проверки

### 1. MVT_ID в LFPG сохраняет информацию о самолёте

В июле 2025 и июле 2026 сопоставил вылеты с уже скачанными OPDI flight lists:

- нормализованный `CALLSIGN_flt`, иначе `FLIGHT_mvt`, и `ADEP_mvt`;
- ближайший `first_seen` в пределах ±1800 с от `MVT_TIME`;
- пробелы удалены с краёв позывного **с обеих сторон**;
- строковые времена OPDI 2026 явно преобразованы в datetime.

Затем отсортировал вылеты по `MVT_ID_mvt`. Результаты относятся к сопоставленным записям и оценивают согласованность с OPDI, а не независимо удостоверенную точность идентификации.

| Проверка LFPG | Июль 2025 | Июль 2026 |
|---|---:|---:|
| Пары сопоставленных вылетов с разницей ID ровно 1 | 19 031 | 20 485 |
| Доля пар с одинаковым `icao24` | **85,13%** | **84,84%** |
| Средних записей, у которых ID−1 и ID+1 имеют одинаковый борт | 13 586 | 14 935 |
| Совпадение борта средней записи с двумя соседями | **13 558 / 13 586 = 99,79%** | **14 894 / 14 935 = 99,73%** |
| Несопоставленных средних записей с такими согласующимися соседями | 679 | 339 |

Для контроля: доля одинакового борта у соседних ID в июле 2025 практически нулевая у EDDF/EGLL/LIRF и 0,25% у EHAM. Эффект специфичен для порядка записей LFPG.

Ещё одна проверка: группы определялись **только по данным челленджа**, с новой группой при разрыве ID, обратном ходе времени взлёта или смене типа ВС. Доля сопоставленных строк, соответствующих самому частому борту своей группы, — 97,09% в 2025 и 96,55% в 2026. Получилось 2899/2828 групп; 373/441 из групп с известными бортами смешивают несколько бортов. Поэтому это вероятностная связь, не готовый tail ID. Групповые номера между месяцами не сопоставимы.

**Что это даёт:** можно исследовать историю конкретного самолёта, предыдущие/следующие движения и происхождение неправдоподобных block times. Прежнее «тот же номер рейса обычно рулит нормально» этого не проверяло: номер рейса и борт — разные сущности.

Две большие январские ошибки LFPG повторно найдены в исходных данных: `182378789 / EJU983W`, y=84240; `182377662 / EJU42AY`, y=58206. Проверка простого копирования block из прилёта LFPG в тот же момент не дала объяснения. Январская идентификация бортов и механизм этих двух ошибок **ещё не установлены**. Июльский результат нельзя объявлять исправлением январских выбросов.

### 2. У вылета без NM иногда есть NM в записи его прилёта

Сопоставление: вылет без `FLIGHT_ID_mvt` → прилёт с заполненным AOBT, точное совпадение `(ADEP, ADES, FLIGHT_mvt)`, посадка через 10 минут–12 часов после взлёта, ровно один кандидат внутри окна. Это консервативный поисковый фильтр; окончательная проверка идентичности рейса ещё нужна.

| Показатель | Обучение 2025 | Ranking |
|---|---:|---:|
| Кандидаты на восстановление NM через прилёт | **896** | **221** |
| В том числе LIRF | 106 | 36 |
| В том числе LFPG | 183 | 37 |

В текущей валидации нашлось 272 таких вылета, их SSE текущей модели — 6,012·10⁸. Даже идеальное исправление **всего** этого среза даёт максимум около 2,79 с полного RMSE на валидации: это полезный дополнительный канал, а не самостоятельный путь в топ-3.

У восстановленного AOBT ошибка относительно истинного block имеет медиану +62 с, но максимум +86574 с. **Нельзя просто заполнить исходные NM-колонки и запустить прежний клип LOBT.** Окно ±3606 доказано для исходного сопоставления организаторов; оно не становится ограничением для повторно найденного рейса. Сохранить исходный `has_nm`; новые времена хранить отдельно, вместе с вероятностью правильного сопоставления.

Контроль: у исходно сопоставленных по `FLIGHT_ID_mvt` пар вылет–прилёт нашлось 315 269 пар в обучении и 50 923 в ranking; конфликтов AOBT между двумя записями — 0. На них можно измерять точность алгоритма повторного сопоставления, скрывая ID у вылета.

### 3. OPDI полезен для бортов даже при плохом покрытии поверхности

По тому же предварительному сопоставлению:

| Показатель | Июль 2025 | Июль 2026 |
|---|---:|---:|
| Сопоставлено вылетов | **169 095 / 190 713** | **175 106 / 192 122** |
| Из них исходно без NM | **2441** | **1720** |
| LIRF без NM | 294 | 236 |
| LFPG без NM | 602 | 385 |

Среди кандидатов для этих noNM-строк внутри выбранного окна не было нескольких разных `icao24`. Это не доказывает отсутствие ошибочных совпадений, но делает проверку ротаций практически осуществимой.

В `src/opdi_check.py:26–36` позывной PRC очищается, а OPDI `flt_id` перед join не очищается. В локальных flight lists есть значения вроде `AFR722  `. Кроме того, `first_seen` в файле 2025 имеет тип datetime, а в 2026 — String. Поэтому отрицательные результаты покрытия стоит проверить на корректной нормализации. **Новые числа выше — покрытие flight list, не покрытие off-block событиями**; плохое покрытие наземных событий ими не опровергнуто.

[Официальный каталог OPDI](https://www.opdi.aero/data.html) подтверждает flight lists, идентификаторы бортов, таблицы событий и покрытие январь 2022 — июль 2026. Открытая лицензия конкретной выгрузки по проверенной странице не установлена. Это позволяет исследовать уже скачанные данные, но для включения источника в призовое решение остаётся вопрос условий использования. Альтернатива для новых данных — [архив ADSB.lol 2026 под ODbL](https://github.com/adsblol/globe_history_2026): использовать воздушную часть треков для ротаций, а не требовать координаты у стоянки. Полный год архива не нужен: сначала небольшой заранее выбранный набор дней и нужных бортов.

### 4. «Нет истории в 2025» не означает «нет наблюдений этого рейса»

В ranking 335 строк LIRF без NM с `0 < MVT−SCHED < 4 ч`. При точном совпадении непустого `FLIGHT_mvt` у 191 строки нет истории среди **всех** вылетов LIRF 2025; 19 из них имеют пустой номер.

Из этих 191 строк:

- у **141** номер встречается минимум в 3 разных дня соответствующего месяца ranking;
- у **134** — минимум в 5 днях;
- у **146** есть тот же номер с NM в другие дни этого месяца.

Например, `DLH5AA`, `PGT52EY`, `AEA59RM` наблюдаются в 31 дне июля, обычно с NM. Признаки регулярности доступны без меток вылетов 2026.

Если считать историю только среди noNM-вылетов обучения, неизвестных строк 240, из них 183 повторяются минимум в 3 дня ranking, 189 имеют NM-наблюдения. Это другой знаменатель. Число 198 из предыдущего отчёта данным точным определениям не соответствует; для эксперимента нужно зафиксировать определение истории. Пропуски номера не объединять в один «рейс» и не терять при join.

## Почему «97% остатка неисправимы» не следует из ревью

1. Нулевая поправка среднего по аэропорту/ВПП/стоянке не исключает взаимодействий, последовательностей и дополнительных измерений. Она закрывает проверенные поправки.
2. Калибровка вероятностей по крупным бинам не означает, что режим нельзя различить новым признаком. Можно иметь идеально калиброванную вероятность 0,5 и при этом новый признак, разделяющий два режима.
3. Ошибка `p(1−p)·gap²` является условной дисперсией только при достаточно информативном условии и корректной вероятностной модели. Подстановка вероятностей текущего классификатора не доказывает информационный предел.
4. Неудача TabPFN на прежних столбцах не проверяет TabPFN на восстановленных связях и не проверяет другие постановки задачи.
5. В обзоре литературы есть ограничение «в тесте нет ATOT соседей». Для этого челленджа оно неприменимо: время движения других вылетов оставлено в ranking. [Официальное описание данных](https://prc-data-challenge-2026.netlify.app/data.html) перечисляет скрытые поля вылетов. Здесь допустима ретроспективная реконструкция, а не только прогноз из прошлого.

## Эксперименты в порядке приоритета

### A. Восстановить цепочки бортов и происхождение метки

**Первый крупный эксперимент.** Начать с LFPG и LIRF; получить вероятностные связи «тот же самолёт», «тот же рейс в другом источнике», «предыдущий/следующий сегмент».

Признаки: время с предыдущего прилёта именно этого борта; подтверждённая другая работа самолёта между возможным block и текущим взлётом; длительность стоянки; разрыв ротации; повторное появление того же вылета; изменения позывного; перестановки хронологии в группе ID. Для LFPG сравнить вариант только на структурных признаках ID с вариантом, дополненным внешним бортом.

Это отличается от отклонённого ограничения «предыдущий прилёт на ту же стоянку»: теперь проверяется самолёт, а не место стоянки. Но и здесь физическая невозможность не запрещает ошибочную **записанную** метку. Нужны два слоя: физическое событие и механизм его отражения в BLOCK.

Не начинать с огромной GNN. Сначала восстановленные признаки + текущая модель, отдельно классификатор редких режимов. Граф с вероятностями связей нужен для неоднозначных совпадений; максимум правдоподобия одной связи не должен скрывать альтернативы.

**Проверка:** точность связей на скрытых известных ID; перенос структуры на 2026; OOF-выигрыш полного SSE; отдельно все хвостовые случаи 2025, а не только две уже изученные строки. Для малочисленного механизма оценивать ложные срабатывания на всех обычных строках. Признак 99% точности может быть опасен при ошибке ложного сдвига на сутки.

**Остановить:** связи не дают новой информации о режиме/остатке в отложенных месяцах. Обнаружение самолёта само по себе не гарантирует прироста.

### B. Расписание из самого ranking вместо истории только по номеру

**Самый дешёвый следующий опыт.** Для каждого номера и маршрута строить профиль по немаркированному месяцу: число дней, регулярность по дням недели, циклический разброс времени расписания, число записей с NM, устойчивость типа/оператора/стоянки. Текущую строку исключать из агрегатов, где это существенно.

Связывать сезонные смены номера через `(перевозчик, маршрут, день недели, локальное время расписания)` с вероятностью соответствия, а не жёстко. Историю режима переносить только из обучающих месяцев; из ranking переносить наблюдаемые признаки и NM, не скрытые метки.

Для noNM полезен префикс `FLIGHT_mvt`: текущий `airline_prefix` в features.py берётся только из `CALLSIGN_flt`, которого как раз нет. Искажения вроде повторённого фрагмента позывного нормализовать по подтверждённым соответствиям, сохраняя сырой вариант и признак искажения.

**Проверка:** месяцы 2025 притворяются ranking; наблюдаемые профили строятся внутри этих месяцев, все их BLOCK скрыты. Дополнительный stress-test — целиком новые номера/сезонные семейства. Результат оценивать на срезе без истории, где E14 не помогает, и по полной смеси с CatBoost.

**Остановить:** выигрыш остаётся только у уже известных номеров или пропадает при имитации их смены. Это, вероятно, добавка к крупному направлению A, не замена ему.

### C. Обучать смесь под ошибку финального прогноза

Сейчас `train.py:184–189` обучает multiclass-модель с early stopping по классификационной метрике. Это не математическая ошибка: корректные условные вероятности асимптотически оптимальны и для смеси. Однако при редких классах, ограниченной модели и выборе числа деревьев оптимум logloss может отличаться от оптимума SSE в секундах.

При двух кандидатах `r` и `c`, `g=c−r`:

`prediction = r + p·g`

`loss = (prediction−y)² = g² · [p−(y−r)/g]²`.

Ошибка вероятности 0,1 при расстоянии кандидатов 86400 с даёт ошибку прогноза 8640 с; при расстоянии 600 с — только 60 с. Поэтому одинаковая ошибка вероятности может различаться по цене SSE в 20 736 раз.

Минимальный опыт: сохранить последовательность checkpoint классификатора и выбирать её по SSE **всей смеси** на внутренней валидации. Следующий: небольшой gating-модуль, минимизирующий `(Σ p_k c_k−y)²`, с исходными вероятностями как априором/регуляризацией. Регрессор-кандидат для обучения gate должен быть OOF; иначе обучаем его на слишком точном кандидате.

Вариант для редких режимов: бинарная модель на нормированном расстоянии `(y−r)/g` с весом `g²`, ограничением p∈[0,1] и защитой при g≈0. Многоклассовый вариант лучше оптимизировать через финальный прогноз непосредственно. Взвешенный logloss не тождественен этой функции.

**Проверка:** все шесть внешних фолдов, полный SSE, срезы классов и большие gap, отдельный предел вреда от ложного dayshift. Подбирать регуляризацию внутри фолда. Это не повтор E2/E6: меняются цель обучения и выбор checkpoint, не только калибровка готовой модели.

### D. Совместно восстановить состояние аэропорта из последовательности

**Самый экспериментальный путь с широким охватом.** У нас известна вся последовательность взлётов/посадок. Вместо сумм в окнах представить последовательность событий: интервалы между взлётами, типы предыдущих ВС, посадки между ними, перерывы обслуживания, переключения ВПП, наблюдаемые NM-оценки отхода, движение прилётов к стоянкам.

Начать с небольшой временной модели/модели пространства состояний для скрытой очереди и пропускной способности. Альтернатива — локальный Transformer по событиям одного аэропорта с несколькими головами: обычный taxi-out, поправка к NM, вероятность режима. Двусторонний контекст уместен, поскольку это ретроспективная задача. Разные месяцы нельзя соединять одним непрерывным контекстом.

Очередная физика — мягкая регуляризация, не жёсткий FIFO: самолёты обгоняют друг друга, бывают несколько очередей и ошибочные метки. У `[pushback, takeoff]` одного рейса могут быть многие объяснения; нужен априор и наблюдаемые прокси. Работа [Simaiakis & Balakrishnan](https://web.mit.edu/hamsa/www/pubs/SimaiakisBalakrishnan_TS2014.pdf) даёт прямую очередную модель. Предложенная здесь обратная реконструкция и её польза для этого челленджа — исследовательская гипотеза, не результат статьи.

**Проверка:** сначала один аэропорт и два стресс-периода; ablation против текущих оконных признаков. Оценивать корреляцию ошибок с CatBoost и улучшение бленда. Не переносить опубликованные RMSE других аэропортов на этот набор.

**Остановить:** последовательность не помогает в отложенных месяцах или даёт только повтор имеющихся счётчиков. Простая GNN по статической карте OSM без нового событийного сигнала имеет меньший приоритет.

### E. Использовать прилёты как доступные метки состояния 2026

Новый способ использовать уже имеющиеся данные: по прилётам обучить модель ожидаемого taxi-in и механизма округления/подмены block. Остатки прилётов агрегировать в скрытое состояние `(аэропорт, период, источник/оператор)`. В 2026 эти метки известны, поэтому состояние можно оценить без taxi-out labels.

Общая модель должна иметь **разные** наблюдательные уравнения для прилёта и вылета: нельзя просто прибавить остаток taxi-in к taxi-out. Применения: смена качества данных, общий затор, температура/де-айсинг, временной сдвиг измерений. Аналогично проверить расхождение `ARVT_3` с фактической посадкой связанного рейса как дополнительное измерение ошибки NM; гипотеза общего смещения двух концов траектории пока не доказана.

**Проверка:** валидационные месяцы имеют только разрешённые метки прилётов; параметры переноса между направлениями обучены в других месяцах. Placebo — перемешивание дней прилётов внутри аэропорта. Если перестановка не уменьшает эффект, вероятно, модель использует статическую частоту, а не новое состояние.

### F. Явная модель причин отсутствия NM

E3 проверял дневной признак, а не модель механизма пропусков. Смешиваются минимум: сбой сопоставления, искажённый позывной, выход block за окно, отсутствие плана. В EHAM январь 2026 и LIRF это разные смеси.

Восстановленные парные записи из A и внутренние связи с прилётом дают наблюдения для различения причин. Модель оценивает `P(причина | видимые данные, контекст)` и затем распределение block по причине. Дневной сбой должен ослаблять интерпретацию «нет NM ⇒ плановый block», а не автоматически умножать taxi-out.

Случайное стирание NM у обычных строк не воспроизводит механизм пропусков. Искусственное маскирование полезно для обучения обработки неполных входов, но итоговый тест обязателен на естественных noNM. Если LOBT отсутствует, нельзя объявлять отрицание окна ±3606 доказанным ограничением: неизвестно само значение LOBT и причина отсутствия.

**Остановить:** причины нельзя различить или они не меняют предсказание за пределами уже имеющегося TabPFN. Не строить большой EM-процесс без этого малого подтверждения.

### G. Новая модель на новых представлениях — как дополнительный участник ансамбля

[TabM](https://github.com/yandex-research/tabm) и [TabR](https://arxiv.org/abs/2307.14338) — разумные кандидаты после A/B/D: параметрически эффективный ансамбль нейросетей и обучение с извлечением похожих обучающих примеров соответственно. Их работы не доказывают преимущество на PRC.

Цель опыта — независимая ошибка относительно бустинга. Для TabR исключить метки внешнего валидационного месяца из retrieval; для TabM подавать относительные времена, расстояния кандидатов, мягкие связи и доступные профили 2026. Начать с одного аэропорта/подвыборки, затем проверить полный бленд. Ещё один бустинг на тех же столбцах — низкий приоритет после уже выполненных опытов.

## Новые внешние данные: что действительно стоит добывать

1. **Идентичность борта и история его перемещений**, OPDI flight lists / ADSB.lol. Доказана практическая сопоставимость на июле; наземный ADS-B для этого не обязателен. Начать с января LFPG и ротаций LIRF, затем проверять перенос на все месяцы.
2. **Неполные наземные треки как интервальное свидетельство.** Если самолёт наблюдался неподвижным на своей стоянке в t₀ и уже на рулёжке в t₁, это может ограничить физический отход интервалом. Первый принятый пакет сам по себе off-block не является. Проверять связь с записанной меткой и включать признак покрытия; физический интервал нельзя применять к плановому/ошибочному BLOCK как жёсткую истину.
3. **Детальная топология маршрута и временные ограничения**, только после A/D. В источниках уже найдены OSM и SIA; новизна была бы в переходе к длине путей, местам пересечения ВПП, альтернативным маршрутам и взаимодействию с реальной последовательностью движений. Повторная загрузка той же погоды или ещё одного календаря не создаёт сопоставимого нового сигнала.

Покупка исторических off-block, закрытый A-CDM, недоступный всем участникам архив не включены в план. [Требования конкурса](https://prc-data-challenge-2026.netlify.app/eligibility.html) требуют открытых дополнительных данных и воспроизводимого оригинального решения. Для OPDI нужен проверяемый ответ об условиях конкретной выгрузки; источники с явной открытой лицензией предпочтительнее. Сообщения организаторам в рамках этого анализа не отправлялись.

## Валидация, которая не отсекает редкие открытия заранее

- Сначала зафиксировать контроль: канонический v14/воспроизведённый эквивалент и OOF-прогнозы полного ансамбля. Изменения сравнивать попарно по одним строкам. Подсчитывать суммарную SSE, а не среднее RMSE фолдов.
- Для массового улучшения: шесть внешних фолдов пар месяцев, дополнительный временной holdout в конце года, стресс-месяцы со сбоями. Все параметры подбираются внутри внешнего фолда.
- Для нового механизма редких ошибок нельзя автоматически требовать улучшения в 8 из 12 месяцев: в части месяцев сам механизм отсутствует. В месяце без события проверять ложные срабатывания, а не обязательный выигрыш.
- Удаление топ-3 строк оставить анализом чувствительности, но не универсальным запретом. Если метод заранее восстановил реальное связанное событие для редкой строки, концентрация выигрыша ожидаема. Если метод выбран после рассмотрения её ошибки — нужен новый период/набор событий для подтверждения.
- Показывать одновременно: полный SSE; крупнейшие выигрыши/проигрыши; поаэропортные дельты; естественные noNM; неизвестные номера; январь/июль; покрытие нового источника и качество связей. Дневной/недельный bootstrap полезен, но при двух аномалиях не устраняет неопределённость хвоста.
- Итог E14 проверять на полной смеси. LightGBM-only CV подходит как предварительный отсев, но не как финальное доказательство улучшения CatBoost-бленда.
- Лидерборд использовать для проверки заранее сформированной модели. Официальная страница прямо запрещает попытки учиться на механизме ранжирования; индивидуальное прощупывание меток сабмитами не входит в план.

## Очерёдность работ

Оценки ниже — план исследования, не обещание срока обучения на имеющейся машине.

| Порядок | Работа | Дешёвый решающий результат |
|---|---|---|
| 1 | Внутренние пары вылет–прилёт + профиль новых номеров | Проверка совпадений, новые признаки, полная OOF-дельта; никакого автоматического LOBT-клипа для восстановленных NM |
| 2 | LFPG: группы ID → ротации → модель источника метки | Январские борта/хронология, все аналогичные события 2025, ложные срабатывания на обычных строках |
| 3 | Checkpoint и gate смеси под SSE | Улучшение полного прогноза на внутренних/внешних фолдах, а не только logloss |
| 4 | Один прототип событийной модели + состояние по прилётам | Полезная независимая ошибка на отложенных месяцах одного аэропорта |
| 5 | Расширение источников/аэропортов, TabM/TabR | Только если предыдущие пробы подтвердили новый сигнал |

По доступным доказательствам обещать топ-3 нельзя. Но стратегия «после E14 новых рычагов нет» уже не соответствует исследованному состоянию данных: появились измеримые связи, которых нынешняя модель не использует. Главный шанс — научиться восстанавливать событие и механизм записи BLOCK, сохранив сильный текущий ансамбль как контроль.
